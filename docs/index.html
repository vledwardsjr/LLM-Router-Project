Executive summary

Given a query, can a classical ML classifier predict — before calling either model — whether a cheap/fast LLM (Haiku 4.5) will give a "good enough" answer, or whether the query needs a larger/expensive model (Sonnet 5)? This project built the labeled dataset, engineered query-only features, trained and compared two classifiers, and produced a cost-savings-vs-quality-loss tradeoff curve — the business-facing deliverable a real routing decision would be made from.

Headline result

A Logistic Regression router, operated at a threshold chosen to bound worst-case quality loss, routes 36.4% of traffic to the cheap model while improving average response quality and capping the worst single-query quality loss at 3 points on a 10-point scale (vs. 7 points with no routing safeguard at all). The simpler, regularized model outperformed XGBoost on this dataset — a finding backed by cross-validation, not a single lucky split.

Every number in this report is pulled directly from the saved pipeline outputs, or from live tests against the deployed endpoint — nothing is rounded from memory.

§1

Dataset construction

Query set: 3,000 queries sampled from databricks/databricks-dolly-15k across 8 task categories, then a stratified subsample of 900 queries (same category proportions) to keep API cost bounded.

Dual-model runs: every query sent to both a small model (claude-haiku-4-5) and a large model (claude-sonnet-5) via the Anthropic Batch API — 1,800 calls, 900/900 rows succeeded, zero permanent failures. Actual cost: $3.23.

Independent LLM-judge scoring: a third model (claude-opus-5, independent of both candidates to avoid self-preference bias) scored each of the 1,800 responses individually — never comparatively — on correctness, completeness, and quality, plus an overall "good enough" score. 1,800/1,800 scored, zero failures. Actual cost: $6.63.

The strict correlation gate technically failed. Diagnosis: two of the 75 validated items (2.7%) — a malformed query where the model appropriately asked for clarification, and a genuinely ambiguous classification puzzle — drove a 5–6 point human/judge disagreement each. Excluding just those two raises Pearson to 0.733. Three independent agreement statistics all landed in the same 0.62–0.63 band, ruling out a metric-specific artifact. Decision: proceed with the existing judge scores, documenting this as a known limitation rather than spending additional budget re-scoring.

Label derivation: label = 1 ("small model is good enough") if large_score − small_score ≤ 1, else 0. Result: 832 label=1 (92.4%), 68 label=0 (7.6%) — a substantial class imbalance carried into every subsequent phase.

Total Phase 1 API spend: $9.86

§2

Feature engineering

Every feature is derived from the query text alone — the entire premise is predicting before either model is called, so response-level signals are out of bounds by design.

Free features: length metrics and regex-based density proxies for numeric/named-entity content (a documented lightweight stand-in for a full NER model). LLM-extracted features: one combined Haiku call per query returning reasoning-step count, ambiguity score, domain, and question type as structured JSON — 900/900 succeeded, cost $0.35.

§3

Modeling

Categorical features one-hot encoded to 24 total. A stratified 80/20 split (720/180 rows) was used given only 68 label=0 rows exist total — an unstratified split risks an unbalanced test fold by chance.

Baseline: Logistic Regression (class_weight="balanced"). Main model: XGBoost, deliberately regularized (shallow trees, subsampling, explicit L2) — the default configuration overfit badly given only 54–68 label=0 training examples.

A finding worth defending, not glossing over

A single 80/20 split gave XGBoost an ROC-AUC of 0.505 — indistinguishable from random — against Logistic Regression's 0.650. Rather than accept that, 5-fold stratified cross-validation was run (the test fold has only ~14 label=0 examples, too few to trust alone):

Logistic Regression0.7090.0430.653 – 0.758

The single-split XGBoost score was an unlucky fold — but even the CV-corrected picture shows Logistic Regression is the stronger, meaningfully more stable performer. A legitimate outcome given the tiny minority class: XGBoost's extra flexibility has less to work with and pays for it in variance. Logistic Regression is the recommended model for deployment.

§4

Threshold tuning & Pareto analysis

Out-of-fold predicted probabilities were generated for all 900 rows (5-fold CV) — every row's routing probability comes from a model that never saw it during training. The classification threshold was swept from 0 to 1 in 101 steps.

A real result, not a broken chart

Average quality loss stays at or below zero across the entire threshold range. Even routing 100% of traffic to the small model produces an average change of −0.077 — a slight net gain. Root cause: Phase 1's generous label rule plus judge scores clustering high (mean 8.4, mostly 8–10) — on this specific dataset, skewed toward simpler QA-style queries, the small model is nearly always adequate by this measure. This is a property of the dataset and labeling choice, not a universal claim that routing never matters.

Since average- and P90-based targets are trivially satisfied everywhere, the operating threshold was instead chosen against the worst single-query (max) quality loss among routed-to-small queries — the one risk metric that moves meaningfully across the curve. This reframes what the router contributes: it doesn't move the average (already good) — it substantially cuts tail-risk.

§5

Deployment — live

This is deployed and running, not just designed.

curl -X POST https://cawdqfgrdj.execute-api.us-east-1.amazonaws.com/ \ -H "Content-Type: application/json" \ -H "x-api-key: <key>" \ -d '{"query": "What is the capital of France?"}'

The endpoint requires an x-api-key header (a shared-secret check in the Lambda itself — HTTP APIs don't support the classic REST API "usage plan + API key" feature) so the public URL can't be used to run up API costs anonymously.

Architecture: AWS Lambda (Python 3.11) behind an API Gateway HTTP API, with DynamoDB for decision caching.

A deliberate implementation choice, worth explaining in an interview

The deployed Lambda does not ship scikit-learn/numpy/pandas at runtime. No Docker was available in the development environment, and cross-compiling those packages' C extensions for Lambda's Linux runtime from macOS without Docker is the standard failure point for zip-based Lambda ML deployments. Since the recommended model is linear, its learned parameters were extracted to a small JSON file and inference reimplemented as pure-Python arithmetic — verified to exactly match the original scikit-learn model's output (max difference: 0.0) across all 900 training rows before being trusted for deployment. The only external dependency shipped is the anthropic SDK, whose Rust-based transitive dependencies were obtained as precompiled Linux wheels via a platform-targeted pip install, again sidestepping the Docker requirement. Deployment package: 4.2MB.

DynamoDB (on-demand billing, 1-hour TTL) caches decisions on a SHA-256 hash of the query text — a latency-critical key-based lookup, not a relational join, which is why DynamoDB was chosen over RDS. Verified live: an identical repeat request returned "cached": true.

IAM: the Lambda execution role is scoped to basic execution plus GetItem/PutItem on only the one table — not broad DynamoDB access.

Limitation confirmed on the live endpoint, not just locally

A genuinely hard, out-of-distribution query — "design a fault-tolerant distributed consensus algorithm and compare it against Raft and Paxos" — was routed to the small model with 99.85% confidence against the live API. Almost certainly wrong. The training data contains very few queries resembling real technical/systems-design questions, and query_word_count's effect on the label runs backward on this dataset (longer queries more often "small is fine") because Dolly's long queries usually embed their own reference context — this query is long without that context. This is a generalization limitation of the training distribution, not a code defect. A production deployment on materially different traffic would need retraining and re-validation first.

§6

Major limitations

  1. Small minority class. Only 68 of 900 examples are label=0 — every Phase 3–4 evaluation should be read with wide confidence intervals in mind.
  2. Judge/human correlation gate technically failed (0.62 vs. a 0.70 target), though within-1-point agreement was strong (85%). A judgment call under budget constraints, not a clean pass.
  3. The "quality never degrades" result is dataset-specific — a consequence of a generous label threshold and a query distribution skewed toward simple tasks, not a universal claim about routing.
  4. Out-of-distribution generalization appeared to fail on manual testing. The router is validated against Dolly-style traffic only — the most important caveat for deploying on different traffic.
  5. Simple heuristics stand in for two components that would ideally be more sophisticated: regex-based entity density instead of a full NER model, and a live per-request LLM call for 4 of 9 features.
  6. The deployment IAM user used broad permissions for setup speed in a personal sandbox account — not what a real production provisioning process should use.
